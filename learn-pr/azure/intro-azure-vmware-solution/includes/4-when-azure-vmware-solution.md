Choose Azure VMware Solution (AVS) when you need to move a compatible application without redesigning it and there's value in keeping vSphere. For example, an application vendor might require vSphere for support. Your team can reuse its VMware skills, but still needs to plan Azure networking, permissions, and the migration.

For workloads with [data residency requirements](/azure/cloud-adoption-framework/ready/azure-setup-guide/regions#check-data-residency-and-compliance), check where the application data, all backup copies, and the recovery site would reside. If no supported AVS region and recovery design meet those requirements, keep the workload in an approved location.

These examples show where AVS can help and what your team still needs to do:

| Business need | How AVS can help |
|---|---|
| Rehost an existing application | Use Azure Migrate to [assess VM requirements and dependencies](/azure/cloud-adoption-framework/azure-vmware-solution/migration). Check that the [guest OS is supported on the target ESXi version](/azure/azure-vmware/ecosystem-os-vms) and that the application vendor supports this configuration on AVS. Choose a [migration method](/azure/azure-vmware/architecture-migrate) and agree on a cutover window. HCX vMotion can move a running VM; bulk migration shuts it down at the source and starts it at the destination. |
| Reduce your datacenter footprint | Measure application response time before the move. If an application makes frequent calls to its database, move both tiers together when the extra round trips between sites would make it too slow. Before retiring the source hardware, test the application and its dependencies from the users' location and [compare response time with the baseline](/azure/cloud-adoption-framework/azure-vmware-solution/migration#41-post-cutover-production-readiness). |
| Prepare for disaster recovery | Use an AVS private cloud as a recovery target for on-premises workloads. Choose protection based on how much downtime and data loss you can tolerate. Before starting a recovered VM, choose a [test network](/azure/cloud-adoption-framework/azure-vmware-solution/operations-health-management#610-recovery-testing-standard). Use an isolated network by default. For a test that needs connected services, prevent address conflicts with production and block writes to live application data. For replicated VMs, run a test failover. For backups, choose a solution that supports restoring your on-premises VMs to AVS and test a restore there. In either drill, verify that the application and its dependencies work and that recovery time and data loss meet your targets. Provisioning the target alone doesn't protect the source VMs. |
| Modernize in stages | Keep the application on vSphere while it uses Azure services. You can move individual components to native Azure services when the application is ready. |

> [!NOTE]
> A guest OS can be compatible with ESXi even after its publisher stops providing routine updates. Check the publisher's support dates; rehosting doesn't change them. For HCX vMotion or replication-assisted vMotion, also [check that the destination hosts support the CPU features the running VM needs](https://knowledge.broadcom.com/external/article/452249/troubleshoot-cpu-hardware-compatibility.html). If they don't, consider a supported method that restarts the VM, such as HCX bulk migration, and agree on the downtime before cutover.

[Metro South Health](https://www.microsoft.com/en/customers/story/1503899547462355298-metro-south-health-provider-azure-vmware-solution) needed more capacity as its hardware approached end of support. The team used Azure Migrate for discovery and assessment, then moved two production VMs to AVS while keeping other VMware workloads on-premises. That hybrid approach added capacity without requiring the whole estate to move at once.

If a small group of VMs can run on Azure Virtual Machines without VMware dependencies, [compare that option](/azure/cloud-adoption-framework/azure-vmware-solution/strategy#when-to-use-azure-vmware-solution) before committing to a dedicated AVS cluster.
