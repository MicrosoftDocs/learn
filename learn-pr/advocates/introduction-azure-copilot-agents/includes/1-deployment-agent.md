Use the Azure Copilot Deployment agent to design infrastructure for a **new workload**. Describe what the workload needs to do, review the proposed design, and turn the approved plan into infrastructure as code. You decide whether and where to deploy it.

> [!NOTE]
> In the Azure portal, open **Azure Copilot > New chat** to select Deployment, Catalyst, Optimization, Resiliency, or Troubleshooting. Start an Observability investigation in **Azure Monitor** instead, for example from a fired alert that offers **Investigate**. Deployment, Catalyst, Observability, and Troubleshooting are generally available; Optimization and Resiliency are in preview. See [Azure Copilot agents and entry points](/azure/copilot/agents).

These instructions apply to Azure public cloud. Azure Copilot [isn't available in Azure Government or Azure operated by 21Vianet](/azure/copilot/overview#pricing-and-availability). In public cloud, if you can open Copilot but can't find a particular agent at its entry point, ask your tenant administrator whether the agent has rolled out and is [enabled for your tenant](/azure/copilot/manage-access#manage-enablement-of-azure-copilot-agents).

If the Copilot button shows **Unauthorized**, ask your tenant administrator to check [Copilot access for your user or group](/azure/copilot/manage-access#manage-user-access-to-azure-copilot-and-agents). If you have access but chat can't connect, ask your network administrator to check the [required WebSocket connection](/azure/copilot/overview#pricing-and-availability) to `https://directline.botframework.com`. Granting resource roles won't fix either problem.

Access to chat doesn't grant access to resources. In an interactive session, Azure role-based access control (RBAC) limits what Copilot can read or change at the target scope. Copilot asks for confirmation before changing resources; confirming doesn't override those permissions.

## Design a new workload

Keep passwords, tokens, and connection strings that contain credentials out of your prompts.

Select **New chat > Deployment** and ask: “Design a highly available web application with a front end, an API, a database, and monitoring.” Tell the agent whether this is a production workload, which region you need, and what failures the app must tolerate. A proposed design might use Azure App Service for the front end and API, Azure SQL Database for storage, and Application Insights for monitoring.

The agent uses Azure Well-Architected Framework guidance to explain trade-offs. For the web app, ask how the design would keep serving requests if a zone failed and what the extra capacity would cost. Use the [Azure pricing calculator](/azure/cost-management-billing/costs/pricing-calculator) with your expected region, service tiers, and usage to check the estimate yourself.

For a new analytics pipeline, ask: “How can we ingest events with Azure Event Hubs, process them in Azure Databricks, and make the results in Azure Data Lake Storage available to Power BI?” Review how data moves between services and which identity needs access at each step before accepting the network and permissions design.

The [portal Deployment agent](/azure/copilot/deployment-agent#current-considerations-and-limitations) doesn't import, analyze, or modify a live deployment. If you need to add a subnet to an existing network, ask Azure Copilot for general guidance, then edit the configuration that already manages the network. Review that change against its existing state rather than applying a template for a new network.

## Review the files and choose how to deploy

:::image type="content" source="../media/deployment-review-paths.svg" alt-text="Diagram that shows how a Bicep what-if preview differs from the saved Terraform plan an authorized deployer applies.":::

1. **Approve the design and choose Terraform or Bicep.** The agent generates files in the artifact pane. Inspect and edit them in the embedded editor or open them in Visual Studio Code for the Web. Check the target subscription and resource group, region, service tiers, and network access. Approving the design generates code; it doesn't create resources.
2. **Check your organization's requirements.** For example, inspect the tags and resource names. A generated tag isn't proof of compliance: [Azure Policy](/azure/governance/policy/overview) evaluates assigned rules and can enforce them. [Azure Resource Graph](/azure/governance/resource-graph/overview) queries existing resource data; it doesn't certify a proposed design.
3. **Choose the deployment or review path.** Inspect the files you plan to share, including parameter files. Don't commit secrets to GitHub, even as literal values for [secure Bicep parameters](/azure/azure-resource-manager/bicep/scenarios-secrets). Use a managed identity where supported, or supply secrets from your approved secret store at deployment time. If you download Terraform files, keep [Terraform state](/azure/developer/terraform/store-state-in-azure-storage) out of the repository because it can contain sensitive values.

   To deploy from the portal, review the target and parameters before confirming. To use your own deployment process, download the files. For team review, select **Create pull request**, sign in to GitHub, and choose the repository and branch.
4. **Preview downloaded files before deploying.** For Bicep, run [Azure Resource Manager what-if](/azure/azure-resource-manager/bicep/deploy-what-if) at the intended scope with the deployment parameters. Compare the output with the approved design. If the API or database is missing, inspect its module and read the [what-if diagnostics](/azure/azure-resource-manager/bicep/deploy-what-if#short-circuiting). Resource Manager can omit resources it can't evaluate; their absence doesn't mean they'll stay unchanged.

   To [see diagnostics for omitted resources](/azure/azure-resource-manager/bicep/deploy-what-if#running-the-what-if-operation), use Azure CLI 2.75.0 or later, or the Az PowerShell module 13.1.0 or later. An older client can omit a module silently. If an expected module is missing, rerun with a current client before approving. If you lack permission at that scope, have the authorized deployment team run the preview.

   For Terraform, initialize the intended working directory and backend. If someone will deploy later, [save the plan](/azure/developer/terraform/create-resource-group#create-a-terraform-execution-plan) with `terraform plan -out=reviewed.tfplan` using the intended inputs. Inspect it with `terraform show reviewed.tfplan`. Keep the saved plan out of Git and restrict access: it can contain sensitive values even when the terminal masks them.

   If you expect a new web app but either preview shows an existing resource being modified in place, replaced, or deleted, stop. Compare the full resource ID and the changed properties with the approved design. For example, redeploying a virtual network in Bicep can reset omitted properties even in [incremental mode](/azure/azure-resource-manager/templates/deployment-modes#incremental-mode). Referencing the network with `existing` doesn't redeploy it. Resolve unexpected changes with the resource owner, check the scope, inputs and, for Terraform, the state, then rerun the preview. A preview predicts changes; it doesn't deploy them or guarantee success.

5. **Deploy the reviewed files or hand them off.** If your role ends at review, give the files and approved target to the deployment owner. Otherwise, use the deployment path for the files you reviewed:

   - **Bicep:** The authorized deployer submits the [reviewed template and parameters](/azure/azure-resource-manager/bicep/deploy-cli#deploy-local-bicep-file) to the same subscription and scope used for the preview. For a resource group, `az deployment group create` with [`--confirm-with-what-if`](/azure/azure-resource-manager/bicep/deploy-what-if#what-if-commands) shows the predicted changes and prompts before deploying. If the inputs, target, or environment have changed, review a fresh preview. Decline unexpected changes.
   - **Terraform:** Once the saved plan is approved, apply that exact file with `terraform apply reviewed.tfplan`. This command doesn't prompt again. If the target, configuration or inputs change, or Terraform rejects a stale plan, generate and review a new one. If you didn't save a plan, an interactive `terraform apply` creates a new plan: review it before confirming.
6. **Verify the result after deployment.** Check that the deployment or Terraform apply succeeded and that the expected resources exist in the intended subscription and resource group. If you provisioned only the App Service infrastructure, verify the site and its configuration, then tell the application team it still needs to [deploy its build](/azure/app-service/deploy-best-practices#deployment-components). If the intended build is deployed, test a known API operation from an allowed client and check for the expected result. A response from the host alone doesn't verify the app or its database connection.

A pull request proposes files; it isn't itself a deployment. Your repository's configured pipelines and approvals determine what runs. The agent can explain how to set up continuous integration and continuous delivery (CI/CD), but it doesn't configure that integration automatically. See the [Deployment agent workflow](/azure/copilot/deployment-agent#example-workflow).
