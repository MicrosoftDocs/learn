ContosoLinuxA's worker logged a `user.warning` completion after `10:00 UTC`, but the order desk still sees only earlier completions. The engineer takes the completion ID from the Linux journal and asks two questions: did the rule in effect on this VM select that message, and which workspace should have received it?

The collection contract is what you expect to happen to a message: which VM produces it, which messages qualify, and where they should arrive. Azure Monitor Agent (AMA) runs in the guest and collects the data specified by a data collection rule (DCR). A rule association links that DCR to a VM. The agent authenticates using the VM's managed identity: Azure maintains the credentials rather than asking you to supply a password. The agent needs network access both to retrieve its settings and to upload records.

On a Linux VM configured with rsyslog, that background service receives Syslog messages and forwards them to AMA. Finding a message in the Linux journal proves it was logged locally, not that rsyslog forwarded it. Inspect the installed forwarding settings: rsyslog may send to a local TCP port (a network listener on the VM) or to a Unix-domain socket (a local connection between processes).

Read `user.warning` as two labels. The **facility**, `user`, is a category for application messages, not the identity of a signed-in user. The **severity**, `warning`, is the importance the sender assigned. A minimum of **Warning** collects warnings and more severe messages for that facility; **Error** excludes warnings. Inspect the level for the individual facility or read the rule definition. The editor's bulk-selection checkbox doesn't indicate whether that facility is enabled.

On Windows, AMA subscribes to selected event log channels. A **channel** is a named log such as Application; a **provider** is the source that writes the record. Windows level selections aren't Syslog minimums: selecting Error alone doesn't collect Information events. In the example, check the Application channel, provider `OrderWorker`, Information level, and numeric Event ID `4100` against a local record. If the rule uses a custom XPath filter, test the expression with `Get-WinEvent -LogName Application -FilterXPath` using only the part after `Application!`. A valid expression can still return no matching records.

Heartbeat proves one communication path recently worked. It doesn't prove that the correct source was emitted, selected, forwarded, transformed, or queried. A missing stream on either OS isn't, by itself, a reason to reinstall AMA.

If you can see the event in the guest but can't find its destination record, run these checks in order:

1. Record the unique completion ID and UTC timestamp from the payload. Also record the Syslog tag, facility, and severity on Linux, or the channel, provider, Event ID, and level on Windows.
1. Verify that the local logging service (rsyslog or Windows Event Log) and AMA are running. Inspect errors from the incident interval.
1. Start with the VM's resource ID and list **all** of its DCR associations. One DCR's **Resources** page shows which VMs use that rule, not every rule used by one VM. Check the event against each relevant source filter. The example rules emit `Microsoft-Syslog` or `Microsoft-Event`. Follow each stream's `dataFlows[].destinations` names to `destinations.logAnalytics[]` and its `workspaceResourceId`. An overlapping rule can send another copy.
1. Compare the saved source filter with the agent's downloaded settings, which may lag behind. Inspect each relevant flow in the **collecting DCR**: if it has inline ingestion `transformKql`, would the row pass, and would its occurrence ID survive? A cloud filter can drop an uploaded row without an error; it doesn't cancel a copy sent by another flow.
1. If the deployed rule uses **multi-stage transformations (preview)**, start at its `syslog` or `windowsEventLogs` source entry. Follow the actual `streams` name, any custom `streamDeclarations`, the matching flows and each `outputStream` (if specified) to the destination workspace and table. Follow each `transform` reference to `properties.transformations`: a source transformation runs on the agent before upload; a flow transformation runs at ingestion. A flow uses either `transform` or `transformKql`, not both.

   Check what a row represents in the output table. If there's one row per event, use its actual fields to find the occurrence ID; a transformation may rename or remove it. If the route keeps only counts, compare the expected time bucket and grouping values. A matching bucket supports "aggregate received; individual delivery not observable on this route." It doesn't prove a particular order committed. Don't enable the preview, disable aggregation, change a workspace transformation or add a raw-data route to test this.
1. For cloud processing failures, inspect DCR metrics by stream and, if **Log Errors** was already enabled, `DCRLogErrors` in that diagnostic setting's workspace. Metrics are aggregate, and neither source can tell you what happened to an individual row removed on the agent.
1. Check identity and outbound connectivity errors if configuration is absent or upload fails.
1. After a correction, follow a newly generated event for a defined interval based on normal ingestion lag. A diagnostic message can test delivery, but only the workload can demonstrate an actual completion.

If neither stream arrives, check shared dependencies before editing either filter. For public endpoints, check the subnet's outbound path and the agent's TLS or proxy errors. If the deployment uses AMPLS, verify that each VM can download its rules through its associated configuration DCE and that the destination workspace is reachable through AMPLS. A successful DNS lookup isn't a successful upload.
