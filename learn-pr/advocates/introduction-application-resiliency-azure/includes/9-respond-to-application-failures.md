Previous sections have focused on automated recovery strategies that are critical for high availability. However, sometimes manual intervention is needed. 

**Alerts**. Monitor your application for warning signs that proactive intervention is needed. For example, if you see that SQL Database or Cosmos DB consistently throttles your application, you might need to increase your database capacity or optimize your queries. In this example, even though the application might handle the throttling errors transparently, your telemetry should still raise an alert so that you can follow up. It's recommended to configure alerts on Azure resource metrics and diagnostic logs using thresholds for service limits and quotas. We recommend configuring alerts on metrics because they have lower latency than diagnostic logs. Azure Resource Health also provides out-of-the-box health information that can help diagnose throttling of Azure services.

**Failover**. Configure a disaster recovery strategy in your application. The appropriate strategy depends on your SLAs. For most scenarios, an active-passive implementation is sufficient. Most Azure services support either manual or automated failover. For example, in an IaaS application, use Azure Site Recovery for the web and logic tiers and SQL Always On Availability Groups for the database tier. Traffic Manager provides automated failover across regions.

> [!IMPORTANT]
> Traffic Manager provides DNS-based traffic routing, not recovery of virtual machines or databases. For an active-passive design, configure an appropriate routing method, such as Priority, and health probes that reflect application readiness. Failover depends on failure detection and DNS caching; existing connections aren't moved. Ensure the secondary application and its dependencies are ready before directing users to them. Azure Site Recovery failover must be initiated separately by an operator or configured automation.
>
> Don't treat probes as a strict traffic-isolation mechanism: if all eligible endpoints are degraded, Traffic Manager responds as if those endpoints were online. Test this case and coordinate endpoint activation with application and data recovery.

**Operational readiness testing**. Test both failover and failback for the complete application, including its data stores, web and application tiers, networking, identity dependencies, and traffic routing. Start with controlled tests in a nonproduction environment. Verify recovered data and critical user flows, and record actual data loss against RPO. Measure elapsed time from the simulated outage through validated application recovery against RTO, not just the restore or failover job duration. Document who initiates recovery, the activation criteria, and how the recovered workload is protected again.

**Data consistency check**. After failover or restore, verify that the recovered data meets the application's consistency requirements. RPO describes acceptable data loss; RTO describes acceptable downtime. Consult each service's disaster recovery documentation as well as its SLA.

Supported geo-redundant Azure Storage accounts allow customer-managed planned and unplanned failover. Check account and feature eligibility. Planned failover requires the storage account's primary and secondary endpoints to be available. Unplanned failover can lose writes that haven't reached the secondary region; use the account's Last Sync Time to assess potential loss. After unplanned failover, re-establish geo-redundancy as part of the recovery plan.

Key Vault's built-in cross-region failover is different: Microsoft initiates it on a best-effort basis, only in supported paired-region configurations, potentially after a significant delay. Unreplicated changes can be lost. After failover, the vault is read-only with limited supported operations. Validate these limitations against the application's needs; don't assume that every paired region supports this feature.

> [!IMPORTANT]
> Don't rely on Microsoft-managed Azure Storage failover to meet your application's recovery targets. Configure and test the supported customer-managed recovery approach before an outage.

**Restoring from backup**. If data is accidentally deleted or corrupted, use backups to restore it to a previously known state. Azure Backup helps quickly restore Azure virtual machines from recent backups using the Instant Restore feature, eliminating the need to transfer a backup from vault storage to the customer's subscription and thereby lowering RTO. Restore options include creating a new virtual machine, restoring disks, or recovering a specific file or folder to meet different needs. By configuring backups for Azure Blobs, Azure Disks, and Azure File Shares, you can also restore application data stored in these Azure services. Databases are critical to many applications. Azure Backup provides point-in-time recovery for SQL Server and SAP HANA databases running on Azure VMs. Its documented primary-region log-backup capability supports an RPO as low as 15 minutes when frequent log backups are configured and succeed; monitor actual recovery-point freshness. Secondary-region recovery points can be older. The ability to select a precise restore time within available backup history doesn't mean that backups provide a seconds-level RPO.
