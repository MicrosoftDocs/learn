A change isn't durable if a replacement VM starts with the old image, a renewed certificate never reaches a listener, or a supposedly retired VM still owns the only copy of a record. In each case, check what the next instance or customer will actually use before retiring the previous version.

## Update a scale-set model and verify replacement instances

Suppose the retailer migrates two of the 19 portal pools to a 20-instance Virtual Machine Scale Set. You patch one running instance, but a later scale-out creates an instance with the old OS build. The fix reached the guest, not the **scale-set model** from which new instances are created. Publishing a versioned *application* as in [Roll out fleet software updates](xref:learn.devrel.azure-virtual-machine-fleet-change-control.roll-out-fleet-software-updates) isn't the same as updating the *base OS image*. To make a change survive replacement:

1. **Build a reproducible version**: Use a reviewed image build, for example Azure VM Image Builder publishing to Azure Compute Gallery. Patch and test the image, keep secrets and live data out of it, and replicate the pinned image version to the deployment regions. Retain the previous known-good version. Check that replacing an OS disk won't erase required state.
1. **Promote through a canary**: Start with a separate canary set or another approved isolated test scope. Provision a *fresh* instance from the candidate model. Verify the actual OS build, application transaction, monitoring, backup enrollment where required, and endpoint protection. A healthy manually patched VM doesn't pass this test.
1. **Control the production rollout**: Check orchestration and upgrade policy before changing the model. With manual upgrade mode, existing instances wait for explicit upgrade, but new scale-out instances already use the updated model. With rolling mode, set a bounded batch size, a supported health signal, and unhealthy-instance limits. Account for autoscale and automatic repairs so replacements don't introduce an unapproved image or interrupt a drain. For a regression, stop further promotion, restore the approved image reference in the model, and explicitly reconcile affected instances. Changing the model back alone doesn't restore their disks.

When you configure autoscale, set a minimum that preserves serving capacity during a drain and a maximum the quota and dependencies can support. Allow a new instance time to start and become ready before counting it as spare capacity. Test scale-in too: a worker with an active return must finish or hand off that job before removal. If automatic instance repairs repeatedly replace healthy guests because a shared dependency is down, investigate the health signal instead of repeatedly rebuilding the fleet.

**Report a mixed-version pool**: Nineteen instances report the new build but the twentieth still runs the old build. Check that instance's model status and whether it was created before the model changed. Don't claim 20 of 20: report the remaining instance as pending or explicitly exempt. Confirm the intended build on a fresh instance before declaring that future scale-outs will use it.

Compare what a fresh backend boots in each path. A successful in-place patch is evidence about the running guest, not the image the scale-set model will use next.

## Rotate a certificate or application secret

For a portal that terminates Transport Layer Security (TLS) on each of its 190 public backends, group the listeners by hostname, pool, current certificate thumbprint, expiry, and team responsible for renewing the certificate. One customer connection reaches only one listener. If TLS terminates at a shared gateway instead, rotate at the gateway rather than updating 190 unrelated certificate stores. For a routine rotation, keep the old version available while you verify the new one:

1. **Introduce the replacement**: Publish the approved certificate version in Azure Key Vault with enough overlap before expiry. Use a managed identity with only the access needed to retrieve it. A supported Key Vault VM extension can deliver renewed certificates, but delivery alone doesn't prove the application is serving one. Scope distribution and activation so the canary is the first listener to switch.
1. **Verify the listener**: Bind or reload the canary listener as the application requires. Make a direct TLS connection to that backend using the portal hostname for certificate validation. Compare the presented thumbprint, hostname, chain, and expiry with the release record. If Key Vault and the local store show the new version but the listener still presents the old one, inspect the binding or reload procedure. Don't retire the old certificate or expand the wave.
1. **Retire the old credential last**: Verify every intended backend and the customer endpoint after expansion. For a service secret that supports two simultaneously valid credentials, activate the new one at the upstream service, publish it in the vault, move consumers in waves, and verify a new authentication attempt from each before revoking the old one. If overlap isn't supported, coordinate a maintenance window instead. Record versions and timestamps, never secret values or private keys. A suspected compromise follows incident-response rules rather than the routine overlap period.

## Stop paying for unused capacity without deleting needed state

Use **Cost Management > Cost analysis** to group spend by workload and pool, then compare it with Azure Monitor utilization over a full business cycle. Two pools with the same low average CPU can have different jobs: one may be idle and the other reserved for failover. Check peak traffic, memory, storage throughput, queued work, and recovery commitments before proposing any reductions. Use these examples to decide which group, if any, can release capacity:

| Finding | Decision and evidence |
|---|---|
| A worker pool averages 3% CPU but handles month-end settlement. | Size the pool against the deadline for clearing the peak queue. Compare a right-sized canary with workers on the original size under a similar load. Expand only if the pool can still finish on time with a worker unavailable. |
| A development fleet is needed only during business hours. | With the development workload owner's approval, schedule deallocation and startup, confirm the Azure power state is **Stopped (deallocated)**, and test that the workload starts when needed. A shutdown inside the guest can leave compute allocated and billable. Disks and other retained resources can still incur charges. |
| The portal workload owner proposes retiring several backends after traffic moves to a new pool. | Check remaining capacity and drain only approved members. Observe a representative traffic and job cycle. For each retiring VM, review dependencies, backups, the team responsible for restores, and the delete options for its disks, network interface, and public IP. Distinguish resources unique to the old backends from resources still used by the fleet. |

**Protect retained data during retirement**: In the retirement list, one data disk holds seven years of required records. Hold its deletion until the records retention owner approves the retention location and the backup team demonstrates retrieval. Don't select “delete with VM” for every disk in the batch. After approved retirements, remove obsolete routing, DNS entries, monitoring targets, and role assignments without disturbing shared resources. Reconcile the remaining inventory and costs against the retirement list.
