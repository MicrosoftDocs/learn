Suppose the returns portal needs two changes: an upgrade from application version `4.2.0` to `4.2.1`, and a Windows security update. Treat them as separate changes unless a tested dependency requires them to ship together. For your own application, deploy an exact package version. For operating system updates, use **Azure Update Manager** to assess and install updates offered by each machine's configured update source. Approval for the earlier support-link change covers neither an installation nor a reboot.

## Upgrade an application to a known version

Publish the reviewed `4.2.1` package as a **VM Application** version in Azure Compute Gallery. Include tested installation and update instructions, verify the package signature or hash against the release record, and confirm the version is available in the target region. Assign `4.2.1`, not `latest`, so a later publication can't change what the next wave receives. Before deploying, record the version actually running on each target and confirm whether the old application can still read data written by the new one.

Start with `fc-canary`. If the upgrade restarts the service, confirm the other nine backends in its pool can carry the load, then drain the canary. Check the version reported by the **running application** on that VM and submit a synthetic return using test data. If the installer reports success but the service still reports `4.2.0` or rejects the return, keep the canary out of rotation and hold later waves. If it passes, obtain pilot approval and repeat the version and transaction checks for every pilot member. Report mixed versions by pool so the portal workload owner knows which customers could still reach `4.2.0`. Use the previous package only on affected instances and only if its data format remains compatible.

## Schedule OS security updates and verify compliance

Use Azure Update Manager to assess and patch the approved VMs. Schedule this separately from the application release so that a reboot or failed installation can be traced to the correct change. Use the following checks before moving between waves:

1. **Assess before installing**: In **Azure Update Manager > Machines**, select the approved inventory and choose **Check for updates**. Record each assessment time, missing Windows Knowledge Base (KB) update or Linux package, and any pending reboot. A failed or stale assessment means *unknown*, not *up to date*. Confirm that each VM can reach its configured Windows update source or Linux repository.
1. **Define the window and its contents**: For scheduled patching on Azure VMs, use **Customer Managed Schedules** patch orchestration and a maintenance configuration with **Guest** scope. Set the time zone, duration, target VMs, update selection, and reboot behavior. If approval names specific KBs or packages, clear broad preselected classifications rather than installing every available security update. Allow time to drain traffic, install, reboot if required, and test before returning a VM to service. Check for competing guest reboot policies.
1. **Keep later waves gated**: Assign only the approved canary to the first window. Keep redundant instances in separate waves so a reboot doesn't remove all serving capacity at once. A second schedule isn't an approval gate: don't attach later targets until the canary has completed any required reboot, its service is healthy, and the portal workload owner approves expansion.
1. **Reassess and reconcile**: Review the installation result for each VM, run a fresh assessment, and check the application directly. Record the update identifier, installation result, reboot status, assessment time, and health result against the manifest. If a patch causes a regression, pause remaining waves. Don't assume every security update can be uninstalled; agree on a supported recovery and account for the security risk of reverting it.

**Report patch coverage**: In this separate patch window, 20 portal VMs are approved. Seventeen complete their updates and health checks, one needs a reboot, one installation fails, and one machine hasn't reported. Record **17 of 20 verified**; 170 other portal VMs are deferred and 10 staff VMs are outside this patch request. Schedule the outstanding reboot, investigate the failure, and restore visibility on the silent VM before asking the portal workload owner to proceed.
