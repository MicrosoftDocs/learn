Local AI agents run on a user's device with that user's access. A command-line agent, desktop application, agentic development environment, or code editor extension can read files, run commands, and call internal services. That closeness to the work makes local agents useful, and it also makes them hard to govern. A local agent can be installed in minutes and reach files, credentials, source code, and internal systems before a security team knows it exists. Without visibility into which agents run and what they can reach, you can't assess exposure, enforce governance, or respond to agent-related incidents.

Consider Contoso, where you're an IT or security administrator. Many Contoso employees, mostly developers, use local coding assistants that read project files, run commands, and connect to services. These tools save time, so removing them is not the goal. Your job is to assess how exposed the organization is and identify controls that reduce that exposure without unnecessarily interrupting legitimate work.

This module is a conceptual overview. You explore the risks that appear when local agents reach devices, data, tools, and connected applications, and you learn how to interpret evidence about which agents are present. You also explore how governance and protection controls apply across the agent lifecycle, from discovering and assessing agents to detecting, investigating, and remediating problems. You don't deploy an end-to-end solution. Instead, you practice interpreting risks and choosing controls that fit them.

By the end of this module, you can identify the risks that local agents introduce, match governance and protection controls to those risks across the agent lifecycle, and map discovery, protection, monitoring, investigation, and remediation responsibilities across Microsoft's security and management services.
