Every application that stores data eventually reduces to a small set of operations: read one item, write one item, change part of an item, and write many items at once. Azure Cosmos DB for NoSQL exposes all of them through the SDK, and each one carries a different cost in request units (RUs) and a different correctness guarantee. Choosing the wrong operation rarely breaks an application outright. It quietly inflates the RU bill, or it lets two concurrent requests overwrite each other in a way that only shows up in production.

Imagine you're a developer at Contoso building the data layer for an order-processing service. The service looks up individual orders by their identifier thousands of times a minute, so those reads must be as cheap as possible. It updates a single status field on documents that hold dozens of line items, so rewriting the whole document wastes bandwidth. It writes an order and its related records together, so a partial write leaves the data inconsistent. It loads a product catalog overnight, so that ingest needs throughput rather than atomicity. And two customer-service agents sometimes edit the same order at the same time, so the second edit must not silently discard the first.

This module works through the operation toolbox that solves each of those problems. You start with point reads, the cheapest way to retrieve a known item, then move through the full set of writes: create, replace, upsert, and delete. From there you apply partial document patch to change a single field without touching the rest of the document, configure item time to live so transient data expires on its own, and use ETags to detect competing writes. You finish with the two multi-item options: transactional batch for atomic writes inside one partition, and bulk execution for high-throughput ingest.

By the end of this module, the developer can perform point reads and every write operation with the Azure Cosmos DB SDK. These operations include applying partial updates and item time to live, protecting concurrent updates with optimistic concurrency control, and choosing correctly between transactional batch and bulk execution for multi-item work.
